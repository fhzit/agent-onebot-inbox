# AI advisory retention and deletion: operations design and gaps

**Status: wired, opt-in operational API; not deployed or externally qualified.** Runtime exposes authenticated preview/apply endpoints when advisory processing and explicit retention policy are enabled. There is no scheduler or automatic expiry. Source/tests do not establish deployment, production PostgreSQL qualification, or backup erasure.

## Current state

`src/main.ts` enables retention only with `AI_ADVISORY_RETENTION_ENABLED=true` and requires `DATABASE_URL`, `AI_ADVISORY_RETENTION_POLICY_VERSION=1`, `AI_ADVISORY_RETENTION_DAYS` (integer 1–3650), and `AI_ADVISORY_RETENTION_BATCH_SIZE` (integer 1–500). Retention also requires `AI_ADVISORIES_ENABLED=true`, with advisory classifier configuration and account allowlist, because the route is unavailable unless advisories are enabled. Invalid/missing explicit retention settings fail startup; no helper defaults are used by this configuration path. This is policy configuration, not evidence that any particular deployment has enabled it.

The bearer-authenticated HTTP endpoints are `POST /api/admin/ai-advisory-retention/preview` with `{ "accountId": "..." }`, and `POST /api/admin/ai-advisory-retention/apply` with `{ "accountId": "...", "confirmation_token": "..." }`. The account must be in the configured advisory allowlist and configured accounts. Preview accepts no extra fields, derives cutoff from configured age, and returns bounded candidates/count and `hasMore`; apply accepts only a server-issued token/account match and uses the previously previewed identities. Tokens are one-use and expire after 15 minutes in-process. Each request is capped by the configured batch size; run a fresh preview for each next batch. Unsupported methods return 405; disabled feature returns 503. A configured retention policy without durable PostgreSQL fails startup.

`src/ai-advisory-retention-adapter.ts` uses parameterized PostgreSQL queries, account fencing, strict `created_at < cutoff`, deterministic oldest-first ordering, and deletion by account/message/policy-version identity. Apply runs the bounded deletion in a transaction. It deletes advisory metadata only, not messages or accounts. The advisory table's account/message foreign-key cascades separately remove advisory rows when a parent is deleted; they are not retention expiry.

Preview and apply are recorded through the general persistent audit store when available. Successful preview records cutoff, days, limit, candidate count, and `has_more`; successful apply records requested/deleted counts, days, and cutoff. Failed apply attempts try to record a categorized failure. Audit write on preview/successful apply is awaited, but audit failures are not a comprehensive fail-closed transactional guarantee; apply deletion and its audit record are not one transaction. The `src/ai-advisory-retention-audit.ts` privacy-safe helper has tests but is not the server route's audit integration. The route authenticates only the shared `API_TOKEN` and writes the fixed generic actor `admin`; it does not establish a verified caller/principal identity. The configured account allowlist fences which account can be selected but is not caller-specific authorization. Do not treat these audit rows as identifying which human, service, or token holder initiated an operation, and do not accept an actor identity from request fields or infer one from headers. Reliable identity attribution and distinct retention authorization require principal-based authentication and authorization to be wired end-to-end. No dedicated actor/authorization capability or audit read-back workflow is implemented.

## Operator workflow and limits

1. Enable retention only after approving and configuring a policy version, retention days, and batch size. Protect `API_TOKEN` and use the API only from an authorized administrative environment; the route currently verifies the shared bearer token and validates the account against the advisory allowlist, not a distinct retention permission.
2. Preview one explicit account. Review cutoff, candidates, count, and `hasMore`; preview does not delete. Do not expose message content: candidates are metadata identities.
3. Apply the returned confirmation token for that account. Tokens are held in process memory, so restart loses pending previews; do not rely on tokens across restarts or share them. A token is consumed before deletion begins; after an apply failure, obtain a new preview.
4. If `hasMore` is true, repeat preview/apply. Responses report requested and deleted row counts. Concurrent changes may mean fewer rows are deleted than requested.
5. Record deployment/configuration and verify effects in the supported operational environment before declaring deletion complete.

The advisory retention audit helper has unit tests, and retention route and PostgreSQL adapter/transaction coverage exists in the worktree; these are fixture/source checks, not external database qualification. Before operational acceptance, test against the supported PostgreSQL version for account isolation, cutoff boundaries, batch limits, concurrent deletes, failures/rollback, audit records, and backup/restore procedures. Until that qualification and deployment evidence exist, treat runtime wiring as opt-in capability only, not an assurance of production deletion or complete erasure.
