# Current implementation status

Agent OneBot Inbox remains an Alpha under active development, not the complete product in the supplied specification.

## Current implementation (checked-out worktree)

- Multi-account validation; authenticated OneBot v11 HTTP Event and Reverse WebSocket ingress; deduplication.
- Normalized messages, inbox filters/pagination/context, and persistent Agent inbox state: unread/seen, processed, and dismissed are distinct from QQ read state. Authenticated API supports filtering by one state at a time and marking individual messages processed/dismissed; inbox UI includes state actions, mark-all-seen, and group names. These are inbox features, not provider-side QQ read operations.
- CLI `unread` sends the API's `unread=true` filter (default limit 50). This filters Agent inbox unread state, not QQ platform read state.
- Authenticated account CRUD; PostgreSQL encrypts transport tokens, memory mode is volatile. Account changes require reconnecting provider-side transports manually; management does not install/login to QQ.
- Contact/group/member manual sync and contact-change event refresh are wired in the current worktree, including admin contact-sync UI. Refresh handling coalesces notices per account/list and marks an in-flight refresh dirty so it reruns after changes arriving during that refresh. Priority/watch rules and PostgreSQL-backed Hermes notification queue/worker runtime wiring are also present. Live PostgreSQL migration/queue and real webhook/provider behavior remain unverified.
- History reconciliation has an authenticated raw HTTP preview route wired to a bounded, read-only preview service. Preview does not import or repair messages. These source/test facts do not qualify live provider behavior or the deployed image.
- `GET /metrics` is connected at runtime and emits Prometheus text counters. This does not imply a Redis queue, configured monitoring/alerts, or deployment smoke qualification.
- MCP stdio/HTTP transport entrypoints exist and the main server exposes authenticated `POST /mcp` (`/mcp` returns 401 without the bearer token). Data tools are disabled by default; setting `MCP_DATA_TOOLS=1` registers `inbox_query`, `conversations_list`, `conversation_messages`, `message_get` and the contact tools, scoped to the instance's configured account list (a single-operator opt-in, not a per-caller entitlement model). Without that env var only `service_info` and `system_status` are registered. Transport startup is not evidence of usable tools.

## Still missing or not production-ready

- End-to-end provider onboarding, production transport lifecycle/reconnect integration, and verified NapCat/SnowLuma capability adapters. The lifecycle controller currently exists as a helper with fixture-level tests; it is not integrated into production transport ownership.
- PostgreSQL migrations run at startup and `PostgresMessageStore` is wired into the server runtime when `DATABASE_URL` is set. The latest production container reached healthy readiness with PostgreSQL connected; full provider round-trip and backup/restore are not verified. Outbound sends use `PostgresOutboundIdempotencyStore` in PostgreSQL mode, with migration `0010_outbound_idempotency.sql`; request claims/completions are durable only in that mode. The authenticated admin runtime route lists up to 100 pending records (no retry) and accepts adjudications when the PostgreSQL reconciliation storage is available. Adjudication writes append-only evidence to migration `0013_idempotency_adjudications.sql`; it does not settle/change the outbound ledger, trigger recovery, retry sends, or establish delivery. Migration/live PostgreSQL/deployment qualification remains unverified; this is not an exactly-once guarantee. History preview is wired, while live provider/database behavior remains unqualified; preview does not import or repair messages. Tests/fixtures do not establish live deployment behavior.
- AI advisories：工作树（非已知部署提交 `adcfe7a`）已包含显式 HTTPS 分类器配置、metadata-only 持久化、认证账号范围读取 API 与管理页。尚未通过真实 PostgreSQL/provider/browser 验收。Retention preview/apply API is opt-in, requires explicit configuration and PostgreSQL, uses process-local one-time tokens and a generic `admin` audit actor, has no scheduler, and does not erase backups. It is not production-qualified. MCP data tools remain disabled on both transports pending verified caller-to-account authorization. 详见 `docs/ai-advisory-acceptance.md` 和 `docs/ai-advisory-retention-operations.md`。
- Provider qualification has an authenticated admin checklist/read/write API, memory/PostgreSQL result stores and migration `0012_provider_qualification.sql`; qualification checks remain `unverified` by default. It records operator-supplied evidence and is not an automated live qualification process.
- Sensitive admin operations are recorded for account CRUD, priority/watch-person CRUD, notification configuration/tests, inbox state changes, sends/revokes (including denied attempts), and inbound message ingestion. Validation/transport failures before provider actions are covered where applicable.
- On known deployed commit `adcfe7a`, `get_file` retrieval and attachment upload/send are present in source and runtime-wired, with upload support declared for NapCat only. This is source/commit evidence, not proof of the currently running image or live provider success; real provider E2E remains unverified. Worktree-only changes—including current advisory/retention UI/API, admin contact sync UI, history preview route, and runtime metrics changes—are not attributable to `adcfe7a`. Backup/restore runtime and contact-aware send target resolution visible in the current worktree are also uncommitted and not attributable to the deployed commit/image. AI classification has an opt-in server invocation in deployed source, but its result is transient and not persisted or exposed as a product feature.
- External live PostgreSQL/provider/backup qualification, real QQ/provider end-to-end, security and load testing. Public Cloudflare reachability was checked during the latest inbox fix deployment; this does not replace ongoing production smoke checks.

This remains an Alpha / early-development project, not a finished or production-ready implementation.
