# Current implementation status

Agent OneBot Inbox remains an Alpha under active development, not the complete product in the supplied specification.

## Current implementation

- Multi-account validation; authenticated OneBot v11 HTTP Event and Reverse WebSocket ingress; deduplication.
- Normalized messages, inbox filters/pagination/context, and persistent Agent inbox state: unread/seen, processed, and dismissed are distinct from QQ read state. Authenticated API supports filtering by one state at a time and marking individual messages processed/dismissed; inbox UI includes state actions, mark-all-seen, and group names. These are inbox features, not provider-side QQ read operations.
- CLI `unread` sends the API's `unread=true` filter (default limit 50). This filters Agent inbox unread state, not QQ platform read state.
- Authenticated account CRUD; PostgreSQL encrypts transport tokens, memory mode is volatile. Account changes require reconnecting provider-side transports manually; management does not install/login to QQ.
- Contact/group/member manual sync, priority/watch rules, and PostgreSQL-backed Hermes notification queue/worker runtime wiring. Queue enqueues on inbound messages and a worker polls/delivers; live PostgreSQL migration/queue and real webhook/provider behavior remain unverified.
- MCP and read-only CLI surfaces.

## Still missing or not production-ready

- End-to-end provider onboarding, production transport lifecycle/reconnect integration, and verified NapCat/SnowLuma capability adapters. The lifecycle controller currently exists as a helper with fixture-level tests; it is not integrated into production transport ownership.
- PostgreSQL migrations run at startup and `PostgresMessageStore` is wired into the server runtime when `DATABASE_URL` is set. The latest production container reached healthy readiness with PostgreSQL connected; full provider round-trip and backup/restore are not verified. Outbound sends use `PostgresOutboundIdempotencyStore` in PostgreSQL mode, with migration `0010_outbound_idempotency.sql`; request claims/completions are durable only in that mode. The authenticated admin runtime route lists up to 100 pending records (no retry) and accepts adjudications when the PostgreSQL reconciliation storage is available. Adjudication writes append-only evidence to migration `0013_idempotency_adjudications.sql`; it does not settle/change the outbound ledger, trigger recovery, retry sends, or establish delivery. Migration/live PostgreSQL/deployment qualification remains unverified; this is not an exactly-once guarantee. History reconciliation planner/service and audit helpers exist, but the source inspection found no HTTP/runtime route invoking provider-history preview; the registered admin endpoint reports local consistency audit only. Reconciliation does not import or repair messages. Tests/fixtures do not establish live provider/database deployment behavior.
- AI-classification contracts/adapters and advisory ingress logic exist, and the server invokes classification when explicitly configured. The result is attached transiently to the ingress message object; no default classifier is constructed, and the source inspected does not persist, expose, or deliver that advisory through inbox/MCP/admin surfaces. Treat AI classification as an opt-in, partial runtime hook—not a persisted/user-visible feature or production-qualified integration. Summary/task extraction remains separate; MCP task extraction is registered as a tool, but that does not implement AI message classification.
- Provider qualification has an authenticated admin checklist/read/write API, memory/PostgreSQL result stores and migration `0012_provider_qualification.sql`; qualification checks remain `unverified` by default. It records operator-supplied evidence and is not an automated live qualification process. MCP registers inbox/contact/history/task-extraction tools, not provider qualification or idempotency administration.

- Sensitive admin operations are recorded for account CRUD, priority/watch-person CRUD, notification configuration/tests, inbox state changes, sends/revokes (including denied attempts), and inbound message ingestion. Validation/transport failures before provider actions are covered where applicable.
- Authenticated `get_file` download API is runtime-wired in the baseline, but real provider E2E is unverified. Attachment upload/API, backup/restore runtime, contact-aware send target resolution, and attachment recovery helpers are present only in uncommitted worktree changes; do not describe them as released/runtime-integrated capabilities. AI classification is more than a standalone helper (the server has an opt-in invocation), but its result is transient and not persisted or exposed as a product feature.
- Real QQ/provider end-to-end, security and load testing. Public Cloudflare reachability was checked during the latest inbox fix deployment; this does not replace ongoing production smoke checks.

This remains an Alpha / early-development project, not a finished or production-ready implementation.
